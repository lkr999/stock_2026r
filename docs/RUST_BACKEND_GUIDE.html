Caginalp 캔들스틱 트레이더 — 백엔드 Rust 코드 설명서

이 문서는 backend/ 폴더의 Rust 코드를 처음부터 끝까지 읽어가는 안내서입니다. 프론트엔드(Svelte)는 다루지 않고, 오직 백엔드가 어떻게 짜여 있는지, 각 코드가 왜 그렇게 생겼는지를 파이썬은 다뤄봤지만 Rust는 처음인 사람 기준으로 설명합니다.

1. 이 문서는 무엇인가

먼저 이 프로그램이 전체적으로 무엇을 하는 프로그램인지부터 짚고 시작합니다.

이 백엔드는 한국 주식(eBest/LS증권 OpenAPI) 을 대상으로 캔들스틱 패턴과 단타(VWAP/ORB/EMA) 셋업을 감지하고, 백테스트로 검증한 뒤, 자동으로 모의투자 또는 실전투자 주문을 내는 트레이딩 시스템입니다. 웹 프레임워크로 axum, 비동기 실행기로 tokio 를 쓰는 평범한 Rust REST API 서버이고, 프론트엔드(SvelteKit)가 /api/... 엔드포인트를 호출해 화면을 그립니다.

핵심만 말하면, 이 서버는 크게 다섯 개의 역할을 합니다.

  1. 시세 조회 — eBest 증권사 서버에서 캔들(봉) 데이터를 가져온다.
  2. 패턴/셋업 분석 — 그 캔들에서 매수 신호(캔들 패턴, VWAP 되돌림, 눌림목 등)를 찾는다.
  3. 전략·리스크 판단 — 신호가 실제로 살 만한지, 얼마나 살지, 손절/익절은 어디에 둘지 계산한다.
  4. 백테스트 — 과거 데이터로 그 전략이 통했는지 미리 검증한다.
  5. 자동매매 실행 — 위 판단을 실시간으로 반복하며 실제(또는 모의) 주문을 낸다.

이 문서는 이 다섯 가지가 backend/src/ 안의 어떤 파일, 어떤 함수로 구현돼 있는지를 실제 소스 코드를 인용하면서 한 줄 한 줄 설명합니다. 코드가 이해되면 이 시스템의 동작도 함께 이해되도록 구성했습니다.

2. 파이썬 개발자를 위한 Rust 속성 과외

본문에서 계속 마주칠 문법을 먼저 한 번에 정리합니다. 각 항목은 "파이썬이라면 이렇게 썼을 것" 과 "Rust는 이렇게 쓴다" 를 나란히 놓고 비교합니다. 처음부터 다 외울 필요는 없고, 뒤에서 실제 코드가 나올 때 다시 돌아와 찾아봐도 됩니다.

2-1. 컴파일 언어라는 것

파이썬은 python app.py 를 실행하는 순간 한 줄씩 해석되지만, Rust는 실행 전에 cargo build 로 전체 코드를 기계어로 미리 번역(컴파일)합니다. 이 프로젝트를 실행하면 나오는 caginalp-trader 라는 이름도 backend/Cargo.toml 의 [[bin]] name 에서 정해진 실행 파일 이름입니다. 타입 오류, 존재하지 않는 변수 참조 같은 실수는 실행 전 컴파일 단계에서 전부 걸러지기 때문에, "일단 실행해서 터지는지 본다"는 파이썬식 개발과 달리 "컴파일러가 통과시키면 이미 그런 종류의 버그는 없다"는 감각으로 코드를 읽으면 됩니다.

2-2. 정적 타입과 타입 추론

Python
price = 70000       # 나중에 문자열을 넣어도 안 막힘
price = "칠만원"     # 실행은 됨(런타임에 터질 수도)
Rust
let price = 70000.0;   // f64 로 추론됨
price = "칠만원";       // 컴파일 에러: 타입 불일치

Rust는 모든 변수에 타입이 있지만, let price = 70000.0; 처럼 타입을 직접 쓰지 않아도 컴파일러가 우변 값을 보고 타입을 추론합니다. 이 코드베이스에서 가격·수량 계산에는 대부분 f64(64비트 실수), 종목코드 같은 문자열은 String(소유하는 문자열)이나 &str(빌려온 문자열 조각)을 씁니다.

2-3. 변수는 기본적으로 불변(immutable)

Python
cash = 10_000_000
cash -= 70000  # 항상 재대입 가능
Rust
let cash = 10_000_000.0;
cash -= 70000.0;              // 컴파일 에러!
let mut cash = 10_000_000.0;  // mut 를 붙여야 변경 가능
cash -= 70000.0;              // OK

파이썬은 모든 변수가 그냥 바뀔 수 있지만, Rust는 let 로 선언한 변수가 기본적으로 "한 번 쓰고 다시는 안 바뀐다"는 뜻입니다. 값을 바꿔야 한다면 명시적으로 let mut 를 씁니다. engine.rs 의 State 구조체 필드가 실행 중 계속 바뀌는 것도 그 값을 담는 변수가 let mut s = state.lock().await; 처럼 mut 로 잠겨(lock) 있기 때문입니다.

2-4. 데이터 묶음: struct + impl

파이썬의 class 는 데이터(속성)와 동작(메서드)을 한 블록 안에 같이 씁니다. Rust는 이 둘을 분리합니다 — 데이터 모양은 struct, 그 위에 붙는 함수(메서드)는 impl 블록에 따로 씁니다.

Python
class Candle:
    def __init__(self, open, high, low, close):
        self.open = open
        self.high = high
        self.low = low
        self.close = close

    def body(self):
        return abs(self.close - self.open)
Rust
pub struct Candle {
    pub open: f64,
    pub high: f64,
    pub low: f64,
    pub close: f64,
}

impl Candle {
    pub fn body(&self) -> f64 {
        (self.close - self.open).abs()
    }
}

실제로 src/candle.rs 의 Candle 이 정확히 이 모양입니다. &self 는 "이 메서드가 구조체 값을 읽기만 하고 가져가지(소유하지) 않는다"는 뜻으로, 파이썬의 self 와 비슷하지만 "빌려온다"는 의미가 타입에 명시된다는 점이 다릅니다(소유권은 2-9에서 설명합니다).

2-5. 여러 종류를 하나로: enum + match

Python
from enum import Enum
class Timeframe(Enum):
    M1 = "1m"
    D1 = "1d"

if tf == Timeframe.D1:
    ...
elif tf == Timeframe.M1:
    ...
Rust
pub enum Timeframe { M1, M3, M5, D1 }

match tf {
    Timeframe::D1 => { /* ... */ }
    Timeframe::M1 => { /* ... */ }
    _ => { /* 나머지 전부 */ }
}

src/timeframe.rs 의 Timeframe 이 바로 이 형태입니다. Rust의 match 는 파이썬의 if/elif 사슬과 비슷해 보이지만 결정적으로 모든 경우를 다뤘는지 컴파일러가 검사합니다. 새 타임프레임이 추가됐는데 어느 match 에서 처리를 빼먹으면, 그 즉시 컴파일이 실패합니다 — 파이썬이라면 그 분기를 타기 전까진 발견되지 않았을 버그입니다.

2-6. "없을 수도 있음"을 타입으로 표현: Option<T>

Python
def find_stock(code):
    return by_code.get(code)  # 있으면 값, 없으면 None

s = find_stock("005930")
print(s.name)  # s 가 None 이면 여기서 런타임 에러
Rust
pub fn info_for(code: &str) -> Option<&'static Stock> {
    by_code().get(code)
}

match info_for("005930") {
    Some(s) => println!("{}", s.name),
    None => println!("종목 없음"),
}

파이썬은 "값이 없을 수도 있음"을 그냥 None 관례로 표현하고, 실수로 None.name 에 접근하면 그제서야 런타임에 터집니다. Rust는 애초에 반환 타입 자체가 Option<Stock> 이라서, 값을 실제로 쓰려면 match 나 if let Some(s) = ... 로 "있을 때"와 "없을 때"를 반드시 갈라 써야 컴파일이 됩니다. universe.rs 의 info_for 가 이 패턴 그대로입니다. 자주 쓰는 축약형도 있습니다.

  • opt.unwrap_or(0.0) — 값이 없으면 0.0 을 대신 쓴다.
  • opt.unwrap_or_default() — 없으면 그 타입의 기본값(숫자는 0, 문자열은 "")을 쓴다.
  • opt? — 함수 안에서 값이 없으면 그 자리에서 즉시 None 을 반환하고 함수를 빠져나온다(ebest.rs 의 minute_cts_key 참고).

2-7. 실패할 수 있는 작업: Result<T, E>

파이썬은 실패를 try/except 로 다루고, 함수 시그니처만 봐서는 그 함수가 예외를 던질지 알 수 없습니다. Rust는 "성공하면 T, 실패하면 E" 를 반환 타입에 그대로 적습니다. 이 프로젝트의 HTTP 핸들러들이 즐겨 쓰는 타입이 좋은 예입니다.

backend/src/routers/candles.rs
type ApiResult = Result<Json<Value>, (StatusCode, String)>;

async fn get_candles(State(st): State<AppState>, Path(shcode): Path<String>, Query(q): Query<TfQuery>) -> ApiResult {
    let tf = parse_tf(&q.tf)?;      // 실패하면 즉시 400 에러를 반환하고 함수 종료
    let token = st.token().await?;  // 실패하면 즉시 503 에러를 반환하고 함수 종료
    let candles = st.fetcher.fetch(&token, &shcode, tf).await;
    Ok(Json(json!({ "candles": candles })))
}
  • ApiResult 는 "성공하면 JSON, 실패하면 (HTTP 상태코드, 에러 메시지)" 를 뜻하는 타입 별칭이다.
  • 물음표(?) 연산자 — parse_tf(...)? 는 "성공(Ok)이면 값을 꺼내 계속 진행하고, 실패(Err)면 그 에러를 그대로 함수 밖으로 반환한다"는 뜻이다. 파이썬의 try: ... except: raise 를 한 글자로 압축한 것과 비슷하다.
  • 마지막 줄 Ok(Json(...)) 는 이 함수의 성공 결과를 명시적으로 감싼 것. 파이썬처럼 그냥 return value 가 아니라 "성공/실패" 라벨을 항상 붙인다.

2-8. 소유권과 빌림(ownership & borrowing) — 가장 낯선 개념

파이썬은 가비지 컬렉터(GC)가 더 이상 아무도 참조하지 않는 객체를 알아서 치워줍니다. Rust에는 GC가 없습니다. 대신 컴파일러가 "이 값은 지금 누가 갖고 있는가" 를 컴파일 시점에 추적해서, 다 쓴 값은 그 자리에서 자동으로 메모리가 해제되도록 코드를 생성합니다. 규칙은 단순합니다.

  • 모든 값은 정확히 하나의 변수가 소유한다.
  • 값을 다른 변수에 대입하면 소유권이 이동(move) 한다 — 원래 변수는 더 이상 못 쓴다.
  • 값을 "잠깐 보기만" 하고 싶으면 & 로 빌린다(borrow) — 소유권은 그대로 원래 주인에게 있다.
  • 값을 "잠깐 바꾸기"까지 하고 싶으면 &mut 로 빌린다.
Python (참조는 늘 공유)
def total(positions):
    return sum(p.qty * p.entry for p in positions)

# positions 는 원본 리스트를 그대로 가리킴(별도 규칙 없음)
t = total(open_positions)
Rust (빌리는 방식이 타입에 드러남)
// &self : positions 를 "읽기만" 빌린다 — 함수가 끝나도 호출자가 계속 소유
pub fn total_entered_amount(&self) -> f64 {
    self.positions.values().map(|p| p.entry * p.qty as f64).sum()
}

risk.rs 의 total_entered_amount(&self) 가 실제 예시입니다. &self 라고 쓰여 있으므로 이 함수는 RiskManager 를 읽기만 하고 끝난다는 것을, 코드를 실행해보지 않고 시그니처만 보고 알 수 있습니다. 반대로 pub fn register(&mut self, ...) 처럼 &mut self 가 붙은 함수는 그 값을 실제로 바꾼다는 뜻입니다. 이 문서 곳곳에서 &T, &mut T, T(빌림 없이 소유권째로 전달) 세 가지를 계속 보게 되는데, "읽기만/바꾸기도 함/아예 넘겨버림" 세 단계로 이해하면 충분합니다.

Python 개발자를 위한 요령

처음엔 소유권 규칙 때문에 컴파일러와 씨름하게 되지만, 이 규칙 덕분에 "다른 스레드가 내가 쓰던 리스트를 몰래 바꿔서 생기는 버그", "이미 닫힌 파일 핸들을 또 쓰는 버그" 같은 것이 애초에 컴파일이 안 됩니다. 이 프로젝트가 자동매매 루프를 여러 비동기 작업이 상태를 공유하며 몇 주씩 안정적으로 돌릴 수 있는 이유 중 하나입니다.

2-9. 인터페이스: trait

파이썬의 덕 타이핑(duck typing)이나 추상 베이스 클래스(ABC)에 대응하는 것이 Rust의 trait 입니다. "이 타입은 이런 메서드를 반드시 구현한다"는 계약입니다. 이 코드베이스는 Serialize(serde 크레이트가 제공, "이 구조체를 JSON으로 바꿀 수 있다"는 계약)를 거의 모든 응답 구조체에 #[derive(Serialize)] 로 자동 구현시켜 씁니다.

backend/src/pattern.rs
#[derive(Clone, Serialize)]
pub struct PatternResult {
    pub pattern_name: String,
    pub confidence: f64,
    // ...
}

#[derive(...)] 는 속성(attribute) 이라 부르는 표시로, 파이썬의 데코레이터(@dataclass 등)와 역할이 비슷합니다 — "이 구조체에 Clone(복제 가능), Serialize(JSON 직렬화 가능) 기능을 컴파일러가 자동으로 만들어 붙여라"는 뜻입니다.

2-10. 클로저(closure) — 이름 없는 함수

Python
total_w = sum(w for (_, w) in active)
best = max(candidates, key=lambda c: c.score)
Rust
let total_w: f64 = active.iter().map(|(_, w)| w).sum();
let best = candidates.iter().max_by(|a, b| a.score.partial_cmp(&b.score).unwrap());

|(_, w)| w 형태가 클로저(파이썬의 lambda)입니다. 세로 막대 | | 사이가 매개변수, 뒤가 본문입니다. strategy.rs 의 composite(), pattern.rs 의 여러 .map()/.filter() 체인이 전부 이 형태입니다. 리스트 연산 스타일도 파이썬의 리스트 컴프리헨션과 상당히 비슷합니다 — .iter().filter(...).map(...).collect() 는 [f(x) for x in xs if cond(x)] 와 같은 일을 합니다.

2-11. 비동기: async/await + Tokio

asyncio 를 써봤다면 개념은 그대로입니다 — 네트워크 호출처럼 "기다리는" 작업을 다른 작업이 그 사이에 CPU를 쓸 수 있게 양보하는 것입니다. eBest 서버에 캔들을 요청하는 동안 서버가 다른 요청을 처리할 수 있어야 하므로, 이 코드베이스의 거의 모든 네트워크/락 관련 함수가 async fn 입니다.

Python (asyncio)
async def fetch(self, code):
    resp = await self.client.get(url)
    return resp.json()

asyncio.run(fetch("005930"))
Rust (tokio)
pub async fn fetch(&self, token: &str, shcode: &str, tf: Timeframe) -> Vec<Candle> {
    let rows = self.fetch_uncached(token, shcode, tf).await;
    rows
}

#[tokio::main]

2-12. 여러 작업이 안전하게 공유하는 상태: Arc<Mutex<T>>

자동매매 루프, HTTP 요청 처리, 텔레그램 명령 리스너는 모두 동시에 같은 엔진 상태(보유 포지션, 현금 등)를 들여다보고 바꿔야 합니다. 파이썬이라면 GIL(Global Interpreter Lock) 덕분에 대충 안전한 경우가 많지만, Rust는 그런 안전망이 없는 대신 "여러 곳이 공유해도 되는 값" 과 "동시에 하나만 고칠 수 있게 잠그는 값" 을 타입으로 명시합니다.

  • Arc<T> (Atomic Reference Counted) — "이 값을 여러 곳에서 함께 소유한다". .clone() 을 호출해도 값 전체를 복사하는 게 아니라 "참조 개수"만 늘어난다. 파이썬 객체가 기본적으로 참조로 공유되는 것과 결과는 비슷하지만, 여기서는 그것이 타입에 명시된다.
  • Mutex<T> — "이 값은 한 번에 한 작업만 만질 수 있다". .lock().await 로 열쇠를 받아야 안의 값을 쓸 수 있고, 다 쓰면 자동으로 열쇠가 반납된다. 파이썬의 threading.Lock 과 같은 개념.
backend/src/state.rs
#[derive(Clone)]
pub struct AppState {
    pub engine: Arc<Mutex<Option<Arc<TradingEngine>>>>,
    // ...
}

이 한 줄이 이 프로젝트의 동시성 설계를 요약합니다. "엔진이 아직 시작되지 않았을 수도 있으니 Option, 여러 HTTP 요청과 백그라운드 작업이 동시에 접근하니 Arc 로 공유하고 Mutex 로 잠근다, 엔진 자체도 여러 곳에서 참조를 들고 있어야 하니 안쪽에 또 Arc<TradingEngine>." 라는 의도가 타입 자체에 다 드러나 있습니다. engine.rs, main.rs 전체에서 st.engine.lock().await 같은 코드를 계속 보게 될 텐데, 매번 "지금 이 엔진 상태의 열쇠를 잠깐 빌린다"는 뜻입니다.

2-14. 매크로: vec!, json!, format!

느낌표(!)가 붙은 이름은 매크로 로, 함수처럼 보이지만 실제로는 컴파일 시점에 코드를 대신 써주는 도구입니다. 이 프로젝트에서 가장 자주 보이는 세 가지만 알면 충분합니다.

  • format!("{code} {qty}주 @{price:.0}") — 파이썬의 f-string(f"{code} {qty}주")과 거의 동일하다.
  • json!({"ok": true, "qty": 10}) — 파이썬 딕셔너리 리터럴처럼 serde_json::Value 를 즉석에서 만든다.
  • vec![1, 2, 3] — 파이썬의 [1, 2, 3] 과 같이 동적 크기 리스트(Vec<T>)를 만든다.
여기까지 기억할 것

모든 문법을 외우지 않아도 됩니다. 뒤에서 실제 파일을 읽을 때 "이건 Option 이니까 없을 수도 있다는 뜻", "이건 &mut 이니까 이 함수가 값을 바꾼다는 뜻", "이건 .await 니까 네트워크나 락을 기다린다는 뜻" 정도만 떠올리면 코드의 의도를 따라가는 데 충분합니다. 문법표는 문서 맨 끝 Rust 문법 빠른 참고표 에도 정리해 두었습니다.

  2. #[tokio::main] async fn main() — 프로그램의 진입점. 이 속성이 내부적으로 Tokio 비동기 런타임을 띄우고, 그 위에서 async fn main 을 실행합니다. 이후 이 프로그램 안의 거의 모든 .await 는 이 런타임이 스케줄링합니다.
  3. .env 두 번 로드 — 프로젝트 루트의 .env 를 먼저 읽고, 그다음 backend/.env 를 읽습니다. dotenvy 는 "이미 설정된 값은 덮어쓰지 않는" 라이브러리라, 뒤에 읽는 backend/.env 쪽 값이 실제로는 우선합니다(먼저 있던 게 없을 때만 채워지므로, 더 구체적인 파일을 나중에 읽어 필요한 값만 보충하는 방식).
  4. tracing_subscriber::fmt().init() — 로깅 설정. 이후 코드의 tracing::info!(...), tracing::warn!(...), tracing::error!(...) 가 터미널에 출력되기 시작합니다. 파이썬의 logging.basicConfig() 한 줄과 같은 위치입니다.
  5. Settings::load() — 환경변수를 읽어 config.rs 의 Settings 구조체를 채웁니다(자세한 내용은 config.rs 절). eBest API 키가 비어 있으면 여기서 경고 로그만 남기고 서버는 계속 뜹니다 — 나중에 실제로 시세를 조회하는 시점에 503 에러로 알려주는 방식을 택했습니다(가짜 데이터로 대충 넘어가지 않는다는 이 프로젝트의 원칙).
  6. AppState::new(settings) — eBest 클라이언트, 캔들 캐시, 패턴 감지기, 거래 일지, 텔레그램 알림기 같은 "프로세스 전체에서 하나만 있으면 되는 것들"을 한 번에 만들어 AppState 에 담습니다 (state.rs 절).
  7. 백그라운드 작업 3개를 tokio::spawn 으로 띄움 — ① 3초 뒤 직전 자동매매 설정을 복원하는 자동 재개, ② 보유 포지션 수가 바뀔 때만 텔레그램으로 알리는 감시기, ③ 텔레그램 /chk·/start· /stop 명령을 듣는 리스너. tokio::spawn 은 파이썬 asyncio.create_task(...) 와 같은 역할로, "이 작업을 백그라운드에서 동시에 돌려라, 메인 흐름은 기다리지 않고 계속 진행해라" 는 뜻입니다.
  8. 라우터를 .merge() 로 이어붙임 — routers/ 폴더 안 6개 파일이 각각 자기 담당 엔드포인트 뭉치를 Router 로 돌려주고, main 은 그걸 전부 하나의 앱으로 합칩니다. 각 라우터가 정확히 무슨 엔드포인트를 갖는지는 routers/*.rs 절에서 다룹니다.
  9. TcpListener::bind → axum::serve — 설정된 호스트:포트(기본 0.0.0.0:7001)로 소켓을 열고, 들어오는 HTTP 요청을 위에서 합친 라우터로 무한히 처리하기 시작합니다. 이 호출이 끝나지 않는 한 (즉 서버가 죽지 않는 한) main 함수는 여기서 영원히 멈춰 있습니다 — 파이썬 uvicorn.run(app) 이 블로킹하는 것과 같은 그림입니다.

let st_boot = st.clone();

  • async move { ... } — move 는 이 클로저(비동기 블록)가 바깥의 st_boot 소유권을 통째로 가져간다는 뜻이다. 백그라운드 작업은 메인 함수보다 오래 살 수도 있으므로, 잠깐 빌리는 게 아니라 아예 넘겨받아야 안전하다.
  • sleep(3초) 후 autostart_from_disk 호출 — eBest 토큰 발급 등 초기화가 자리잡을 시간을 준 다음, backend/data/engine_autostart.json 에 저장된 마지막 실행 설정으로 엔진을 되살린다(자세한 내용은 trading 라우터 절).
Python 개발자를 위한 요령

FastAPI/Flask 앱의 @app.on_event("startup") 훅이나 별도 백그라운드 스레드로 "서버 뜰 때 뭔가 미리 해두기"를 해본 적이 있다면, 여기 tokio::spawn 세 줄이 정확히 그 역할입니다. 다만 Rust에서는 별도 스레드를 만드는 대신 같은 비동기 런타임 위에 "동시에 진행되는 작업"을 하나 더 등록하는 것이라, 스레드보다 훨씬 가볍습니다.

4. 전체 구조 한눈에 보기

19개 파일이 어떤 순서로 서로를 호출하는지, 그리고 자동매매 루프 한 바퀴가 어떻게 도는지를 그림으로 먼저 봅니다. 이후 절들은 전부 이 그림 속 어딘가를 확대하는 내용입니다.

요청 하나가 처리되는 경로는 항상 같은 모양입니다: 프론트엔드가 /api/... 를 호출 → routers/*.rs 의 핸들러 함수가 받음 → 핸들러가 AppState 에서 필요한 걸 꺼내 씀(st.fetcher, st.detector, st.engine 등) → 그 도구들이 필요하면 ebest.rs 를 통해 실제 증권사 서버와 통신 → 결과를 JSON으로 응답. 차이는 그 사이에 어떤 분석/의사결정 계층을 거치는가 뿐입니다 — 이 흐름의 구체적인 예시 다섯 가지는 5장에서 그대로 따라가 봅니다.

5. 계층별 모듈 자세히 보기

이제 그림 속 상자 하나하나를 실제 코드로 열어봅니다. 데이터 계층부터 시작하는 이유는, 위쪽 계층(분석·의사결정·실행)이 결국 전부 이 계층이 만들어주는 Candle 하나를 놓고 계산하는 것이기 때문입니다 — 먼저 재료를 알아야 요리법이 이해됩니다.

Layer 1데이터 계층 — 실제 시세의 원천

backend/src/config.rs

config.rs — 환경변수를 하나의 구조체로

역할 한 줄: .env 값을 전부 읽어 Settings 라는 하나의 구조체로 모은다.

파이썬의 os.environ.get("KEY", default) 를 여러 번 반복하는 대신, 이 파일은 타입별로 헬퍼 함수 세 개(s=문자열, n=숫자, b=불리언)를 만들어두고 Settings::load() 안에서 그걸 반복 호출합니다.

backend/src/config.rs
fn n<T: std::str::FromStr>(key: &str, default: T) -> T {
    env::var(key).ok().and_then(|v| v.parse().ok()).unwrap_or(default)
}

pub struct Settings {
    pub ebest_app_key: String,
    pub trading_max_positions: usize,
    pub trading_risk_per_trade: f64,
    // ... (총 20여 개 필드)
}

impl Settings {
    pub fn load() -> Self {
        Self {
            ebest_app_key: s("EBEST_APP_KEY", ""),
            trading_max_positions: n("TRADING_MAX_POSITIONS", 10),
            trading_risk_per_trade: n("TRADING_RISK_PER_TRADE", 0.01),
            // ...
        }
    }
}
  • fn n<T: std::str::FromStr>(...) — 여기서 <T: ...> 부분이 제네릭(generic)이다. 파이썬의 타입 힌트 Generic[T] 와 비슷한데, : std::str::FromStr 는 "T는 문자열에서 파싱 가능한 타입이어야 한다"는 제약(trait bound)이다. 덕분에 n::<usize>("TRADING_MAX_POSITIONS", 10) 도, n::<f64>("TRADING_RISK_PER_TRADE", 0.01) 도 함수 하나로 처리된다 — 파이썬이라면 그냥 아무 타입이나 받고 실행 중에 실패했을 자리다.
  • env::var(key).ok().and_then(|v| v.parse().ok()).unwrap_or(default) — "환경변수 읽기(실패하면 None) → 성공했으면 숫자로 파싱 시도(실패하면 None) → 그래도 없으면 default" 를 한 줄의 Option 체이닝으로 표현한 것. 파이썬이라면 try/except 두 겹이 필요했을 로직이다.
  • eBest 키가 비어 있어도 load() 는 에러를 내지 않는다 — 실제로 API를 호출하는 시점에야 실패가 드러난다(ebest.rs 참고).

연결: main.rs 가 부팅 시 딱 한 번 Settings::load() 를 호출해 AppState 에 넣고, 이후 모든 모듈은 이 값을 state.rs 를 통해 빌려 쓴다.

backend/src/state.rs

state.rs — 모든 핸들러가 붙잡는 공용 상태

역할 한 줄: 프로세스 전체에 하나씩만 있으면 되는 것들(설정, eBest 클라이언트, 캐시, 감지기, 일지, 알림기, 엔진)을 한 곳에 모은다.

backend/src/state.rs
#[derive(Clone)]
pub struct AppState {
    pub settings: Arc<Settings>,
    pub ebest: Arc<EBestService>,
    pub fetcher: Arc<CandleFetcher>,
    pub detector: PatternDetector,
    pub journal: Arc<TradeJournal>,
    pub telegram: Arc<TelegramNotifier>,
    pub engine: Arc<Mutex<Option<Arc<TradingEngine>>>>,
}

impl AppState {
    pub fn new(settings: Settings) -> Self {
        let ebest = Arc::new(EBestService::new(&settings));
        let fetcher = Arc::new(CandleFetcher::new(ebest.clone()));
        Self {
            settings: Arc::new(settings),
            ebest,
            fetcher,
            detector: PatternDetector,
            journal: Arc::new(TradeJournal::new()),
            telegram: Arc::new(TelegramNotifier::from_env()),
            engine: Arc::new(Mutex::new(None)),
        }
    }

    pub async fn token(&self) -> Result<String, (StatusCode, String)> {
        match self.ebest.auth_token(false).await {
            Some(t) if !t.is_empty() => Ok(t),
            _ => Err((StatusCode::SERVICE_UNAVAILABLE, format!("eBest 인증 실패 — {}", "..."))),
        }
    }
}
  • #[derive(Clone)] — 이 구조체를 .clone() 할 수 있게 자동 생성한다. axum은 요청이 들어올 때마다 AppState 를 clone() 해서 핸들러에 넘기는데, 안이 전부 Arc(+데이터 없는 PatternDetector)라서 이 복제는 사실상 "참조 카운트 몇 개 증가"에 불과하다 — 수천 개의 동시 요청이 와도 비싸지 않다.
  • engine: Arc<Mutex<Option<Arc<TradingEngine>>>> — 안에서 바깥 순서로 읽으면 "엔진이 있을 수도 없을 수도 있고(Option) → 있으면 여러 곳이 같은 엔진을 참조하고(Arc) → 이 슬롯 자체는 동시에 한 곳만 고칠 수 있고(Mutex) → 이 Mutex 는 여러 요청이 공유한다(Arc)". /trading/start 가 호출되기 전까지는 None 이다가, 처음 시작될 때 Some(Arc::new(TradingEngine::new(...))) 로 채워진다.
  • token(&self) — 거의 모든 라우터 핸들러가 시세를 조회하기 전에 제일 먼저 호출한다. eBest 인증에 실패하면 가짜 캔들을 만들어 응답하는 대신 HTTP 503과 실패 사유를 그대로 돌려준다 — 이 프로젝트 전체를 관통하는 "실데이터가 없으면 에러를 낸다"는 원칙이 여기 코드로 박혀 있다.

연결: axum 라우터가 .with_state(st) 로 이 값을 등록하면, 모든 핸들러 함수는 State(st): State<AppState> 매개변수로 이걸 받아 쓴다(예: candles.rs 의 get_candles).

Candle 은 이 프로젝트에서 가장 많이 등장하는 타입입니다 — 시가/고가/저가/종가/ 거래량(OHLCV)을 담는 평범한 구조체이고, 캔들스틱 패턴 판별에 필요한 기하학적 계산 (몸통 크기, 위꼬리/아래꼬리 길이, 양봉/음봉 여부)을 메서드로 붙여둡니다.

Timeframe 은 "1분봉, 5분봉, ... 일봉"을 나타내는 enum 입니다. 단순히 값을 나열하는 게 아니라, 각 타임프레임이 어떻게 조회되어야 하는지 (한 봉이 몇 분인지, 한 번에 몇 봉을 가져올지)까지 config() 메서드로 함께 갖고 다닙니다.

  • match self { Timeframe::M1 => ..., ... } — "이 열거값이 무엇이냐에 따라 다른 튜플을 고른다". 파이썬이라면 {Timeframe.M1: (1,500,20), ...}[self] 같은 딕셔너리 조회에 가깝지만, Rust는 모든 경우를 다뤘는지 컴파일러가 검사해준다.
  • mtf_group() — "이 타임프레임의 신호를 검증할 때 참고할 상위 타임프레임 목록"을 정의한다. 1분봉 전략은 5분봉·15분봉이 같은 방향인지 확인하는데 쓰인다(mtf.rs 참고).

연결: Candle 은 candle_fetcher.rs 가 만들어내고, 이후 indicators.rs·pattern.rs·backtest.rs·engine.rs 전부가 &[Candle](캔들 배열의 빌림)을 입력으로 받아 계산한다.

ebest.rs — 유일한 실제 시세 원천

역할 한 줄: 증권사(eBest/LS증권) REST API와 직접 통신한다 — 로그인 토큰 발급/캐싱, 초당 호출 제한 준수, 실패 시 재시도.

이 파일은 이 시스템에서 진짜 데이터가 들어오는 유일한 문입니다. 다른 모든 모듈은 결국 이 파일이 반환한 JSON을 가공할 뿐입니다. 구조를 이해하려면 "토큰 관리"와 "속도 제한"이라는 두 가지 문제를 어떻게 풀었는지 보면 됩니다.

① 토큰 캐싱

증권사 API를 쓰려면 먼저 OAuth 토큰을 발급받아야 하는데, 요청마다 새로 발급받으면 느리고 서버에 부담을 줍니다. 그래서 EBestService 는 토큰을 만료 2분 전까지 재사용하는 캐시를 Mutex 로 들고 있습니다.

backend/src/ebest.rs
pub async fn auth_token(&self, force_refresh: bool) -> Option<String> {
    let mut cache = self.token.lock().await;
    if !force_refresh {
        if let Some(t) = &cache.token {
            if Instant::now() < cache.expiry {
                return Some(t.clone());   // 아직 유효 → 새로 요청하지 않고 재사용
            }
        }
    }
    if let Some(at) = cache.failed_at {
        if at.elapsed() < AUTH_RETRY_COOLDOWN {
            return None;   // 방금 실패했으면 잠시 재시도하지 않는다 (게이트웨이 차단 방지)
        }
    }
    // ... 실제 HTTP POST로 토큰 발급 요청 ...
}
  • if let Some(t) = &cache.token { if Instant::now() < cache.expiry { ... } } — if let 은 "Option 이 Some 인 경우에만 이 블록을 실행한다"는 뜻으로, match 의 한 갈래만 필요할 때 쓰는 축약형이다. 파이썬의 if cache.token is not None: 과 같은 자리다.
  • 실패 직후엔 AUTH_RETRY_COOLDOWN(10초) 동안 재요청 자체를 막는다 — 앱키가 만료된 상태로 여러 요청이 동시에 몰리면 초당 수십 번 인증 서버를 두드려 차단당할 수 있기 때문이다.

② 초당 호출 제한 지키기

backend/src/ebest.rs
const MIN_CALL_INTERVAL: Duration = Duration::from_millis(1100); // ~1 call/sec

async fn enforce_rate_limit(&self, tr_code: &str) {
    let wait = {
        let mut map = self.next_call_at.lock().await;
        let now = Instant::now();
        let slot = (*map.get(tr_code).unwrap_or(&now)).max(now);
        map.insert(tr_code.to_string(), slot + MIN_CALL_INTERVAL);
        slot.saturating_duration_since(now)
    };
    if !wait.is_zero() {
        sleep(wait).await;
    }
}
  • TR 코드(요청 종류)별로 "다음에 호출 가능한 시각"을 HashMap 에 예약해둔다. 여러 비동기 작업이 동시에 같은 TR을 부르려 해도, 각자 자기 차례의 시각을 예약받고 그만큼만 sleep 한다 — 줄을 서는 것과 같다.
  • 이 블록이 { ... } 로 한 번 더 감싸져 있는 이유: 안에서 map(락)을 잠깐 잡았다가 블록이 끝나면 즉시 놓아준다. 그래야 그 뒤의 sleep(wait).await 동안 락을 붙잡고 있지 않아 다른 작업이 자기 차례를 예약할 수 있다.

③ 토큰 만료 시 자동 재시도

async fn post_tr_retry(&self, token: &str, path: &str, tr_code: &str, body: &Value) -> Value {
    let mut result = self.post_tr(token, path, tr_code, body).await;
    if Self::is_token_error(&result) {
        if let Some(fresh) = self.auth_token(true).await {
            result = self.post_tr(&fresh, path, tr_code, body).await;  // 새 토큰으로 한 번만 재시도
        }
    }
    result
}
  • 서버가 "토큰 만료" 에러를 돌려주면, 강제로 새 토큰을 발급(force_refresh = true)받아 딱 한 번만 같은 요청을 재시도한다. 주문(매수/매도) TR은 이 재시도에서 제외된다(is_order_tr) — 전송이 실제로는 서버에 도달했는데 응답만 못 받은 경우 재시도하면 중복 주문이 나갈 수 있기 때문이다.

이 세 가지 장치 위에, stock_price(현재가), fetch_minute_candles /fetch_daily_candles(분봉/일봉), place_order(주문), get_account_balance(잔고), order_fill_status(체결 조회), cancel_order(주문 취소) 같은 공개 메서드들이 얹혀 있습니다. 전부 "TR 코드에 맞는 JSON 요청 바디를 만들고 → post_tr_retry 로 보내고 → 응답 JSON에서 필요한 필드만 뽑아 돌려준다"는 같은 패턴을 반복합니다.

연결: 직접 이 파일을 호출하는 건 candle_fetcher.rs(시세)와 engine.rs/broker.rs(주문·잔고)뿐이다. 다른 모듈은 전부 그 위를 거쳐 간접적으로만 eBest 데이터를 만난다.

candle_fetcher.rs — 캐시를 얹은 캔들 조회

역할 한 줄: eBest 원본 응답을 Candle 로 정규화하고, 짧은 시간 동안은 캐시에서 재사용해 API 호출을 줄인다.

backend/src/candle_fetcher.rs
pub async fn fetch(&self, token: &str, shcode: &str, tf: Timeframe) -> Vec<Candle> {
    let key = (shcode.to_string(), tf);
    {
        let cache = self.cache.lock().await;
        if let Some((expiry, rows)) = cache.get(&key) {
            if Instant::now() < *expiry {
                return rows.clone();   // 캐시 적중 — eBest를 다시 부르지 않는다
            }
        }
    }
    let rows = self.fetch_uncached(token, shcode, tf).await;
    if !rows.is_empty() {
        let mut cache = self.cache.lock().await;
        cache.insert(key, (Instant::now() + Self::cache_ttl(tf), rows.clone()));
    }
    rows
}
  • 캐시 키는 (종목코드, 타임프레임) 튜플이다 — 같은 종목이라도 1분봉과 5분봉은 별도로 캐시된다.
  • TTL(캐시 유효시간)은 타임프레임마다 다르다: 1분봉은 35초, 일봉은 600초처럼 봉이 갱신되는 주기에 맞춰 캐시 수명을 정한다(cache_ttl). 빠른 봉일수록 짧게, 느린 봉일수록 길게 — 신선함과 API 호출 절약 사이의 절충이다.
  • 조회 결과가 비어 있으면(!rows.is_empty() 가 거짓) 캐시에 넣지 않는다 — 실패를 캐시하면 최대 TTL 동안 계속 "데이터 없음"으로 보이기 때문에, 다음 사이클에 바로 재시도할 수 있게 비워둔다.

이 외에 fetch_history() 라는 별도 메서드가 있는데, 백테스트처럼 수백~수천 봉의 긴 과거 데이터가 필요할 때만 씁니다. eBest 한 번 호출로는 최대 500봉까지만 주기 때문에, "연속조회 키(cts)"로 과거 페이지를 최대 4번까지 이어붙여 모읍니다. 이 캐시는 실시간 매매용 캐시와 완전히 분리되어 있어서, 백테스트를 여러 번 돌려도 자동매매 루프의 캐시 타이밍에 영향을 주지 않습니다.

연결: routers/candles.rs, engine.rs, backtest.rs, mtf.rs, market.rs 등 캔들이 필요한 모든 곳이 ebest.rs 를 직접 부르지 않고 이 파일을 통해서만 부른다 — 캐시/정규화 로직을 한 곳에 모아두기 위해서다.

session.rs — 하루 단위 기준선(VWAP·오프닝레인지)

역할 한 줄: 봉마다 "이 봉 시점까지의 당일 VWAP"와 "오프닝레인지 고가/저가"를 미리 계산해둔다.

단타 셋업(VWAP 되돌림, 오프닝레인지 돌파)은 매번 "오늘 장 시작부터 지금까지"를 다시 훑어야 합니다. 이걸 신호를 찾을 때마다 다시 계산하면 느리므로, SessionContext::build() 가 캔들 배열 전체를 한 번 훑으며 봉 인덱스별 값을 미리 배열로 만들어둡니다 — 그 후로는 배열 인덱싱(O(1))만 하면 됩니다.

backend/src/session.rs
pub struct SessionContext {
    pub vwap: Vec<f64>,
    pub or_high: Vec<f64>,   // 오프닝레인지가 아직 안 끝났으면 NaN
    pub or_low: Vec<f64>,
    pub day_start: Vec<usize>,
}

impl SessionContext {
    pub fn build(candles: &[Candle], or_bars: usize) -> Self {
        let mut vwap = vec![0.0; candles.len()];
        let (mut cum_pv, mut cum_v) = (0.0, 0.0);
        for i in 0..candles.len() {
            let new_day = i == 0 || candles[i].date != candles[i - 1].date;
            if new_day { cum_pv = 0.0; cum_v = 0.0; /* ... */ }
            let c = &candles[i];
            let tp = (c.high + c.low + c.close) / 3.0;   // 대표가(typical price)
            cum_pv += tp * c.volume.max(1.0);
            cum_v += c.volume.max(1.0);
            vwap[i] = cum_pv / cum_v;
        }
        Self { vwap, /* ... */ }
    }
}
  • VWAP(거래량가중평균가) 계산은 누적(가격×거래량) ÷ 누적거래량 이다. candles[i].date != candles[i-1].date 로 날짜가 바뀌는 순간을 감지해 누적값을 0으로 리셋한다 — 이게 "일봉 단위로 초기화되는 세션 기준선"의 핵심이다.
  • &[Candle](슬라이스) — 배열 전체를 복사하지 않고 "어디부터 어디까지"만 빌려서 넘기는 타입이다. 파이썬의 candles[a:b] 슬라이싱과 비슷하지만, Rust는 이게 원본 메모리를 그대로 가리키는 얕은 뷰(view)라 복사 비용이 없다.
  • vec![0.0; candles.len()] — "0.0을 candles 길이만큼 채운 벡터를 만들어라". 파이썬의 [0.0] * len(candles) 와 동일하다.

연결: pattern.rs 의 단타 셋업 감지 함수(detect_setups, detect_v2_setups)와 indicators.rs 의 차트용 VWAP/오프닝레인지 지표가 이 구조체를 그대로 읽어 쓴다.

backend/src/indicators.rs

indicators.rs — 보조지표 계산기

역할 한 줄: 이동평균/RSI/MACD/볼린저밴드 등, 차트에 그리고 셋업 판정에도 쓰이는 숫자 배열들을 계산한다.

이 파일의 함수들은 전부 같은 모양입니다 — 캔들 배열을 받아, 캔들과 길이가 똑같은 결과 배열을 돌려줍니다. 워밍업 구간(계산에 필요한 봉 수가 아직 안 찬 구간)은 None(또는 NaN)으로 채워서, 프론트엔드가 인덱스로 그대로 매칭해 그릴 수 있게 합니다.

backend/src/indicators.rs
type Series = Vec<Option<f64>>;

pub fn sma(candles: &[Candle], period: usize) -> Series {
    let c: Vec<f64> = candles.iter().map(|c| c.close).collect();
    let mut out = vec![None; c.len()];
    for i in (period - 1)..c.len() {
        let mean = c[i + 1 - period..=i].iter().sum::<f64>() / period as f64;
        out[i] = Some(mean);
    }
    out
}
  • type Series = Vec<Option<f64>>; — 타입에 별명을 붙인 것뿐이다. "숫자가 있거나 없을 수 있는 값의 배열"이라는 뜻을 반복해서 쓰지 않으려는 용도로, 파이썬의 Series = List[Optional[float]] 타입 별칭과 같다.
  • c[i + 1 - period..=i] — ..= 는 "끝 인덱스 포함" 범위다. 즉 "i를 포함해서 그 앞 period개"라는 뜻으로, 이동평균의 윈도우를 슬라이싱한다.
  • .iter().map(|c| c.close).collect() — 파이썬의 [c.close for c in candles] 와 정확히 같은 일을 한다. Rust는 이런 "순회하며 변형" 체인을 .iter()(순회 시작) → .map()(각 원소 변형) → .collect()(다시 컬렉션으로 모으기) 로 표현한다.

같은 패턴으로 ema(지수이동평균), rsi(Wilder RSI), macd, bollinger(볼린저밴드)가 구현돼 있고, 마지막의 compute_all() 이 이걸 전부 한 번에 계산해 Indicators 구조체(직렬화되어 차트 API 응답이 되는 것)로 묶어줍니다. ema_values· rsi_values·bollinger_values 는 Option 대신 f64::NAN 을 쓰는 "원시(raw)" 버전인데, pattern.rs 의 셋업 판정 로직처럼 Option 을 매번 벗기지 않고 바로 산술 비교하고 싶은 내부용 계산에 씁니다.

연결: routers/candles.rs 가 차트 표시용으로, pattern.rs/market.rs 가 신호 판정용 원료로 이 파일을 가져다 쓴다.

pattern.rs — 매수 신호를 찾아내는 핵심 로직

역할 한 줄: 캔들스틱 패턴(예: 상승장악형)과 단타 셋업(VWAP 되돌림, 돌파 등)을 감지하고, 각 신호의 신뢰도를 계산한다.

① 캔들스틱 패턴 — 망치형(hammer) 예시

backend/src/pattern.rs
fn hammer_shape(c: &Candle) -> (bool, f64) {
    if c.range() < 1e-6 || c.lower_shadow() < c.body() * 2.0 || c.upper_shadow() > c.body() * 0.3 {
        return (false, 0.0);   // 모양 조건 불만족 → 감지 안 됨
    }
    let body_pos = (c.open.min(c.close) - c.low) / c.range();
    if body_pos < 0.60 { return (false, 0.0); }
    let conf = (c.lower_shadow() / (c.body() * 2.0)) * 0.7 + body_pos * 0.3;
    (true, conf.min(1.0))
}
  • 반환 타입 (bool, f64) — "감지됐는가, 신뢰도는 얼마인가"를 튜플로 묶어 돌려준다. 파이썬의 return True, 0.82 와 형태는 같다.
  • 망치형의 조건: 아래꼬리가 몸통의 2배 이상 길고, 위꼬리는 짧고, 몸통이 봉 범위의 아래쪽에 있지 않아야(=몸통이 상단 40% 안에 있어야) 한다 — 이 세 줄의 if 가 그 기하학적 정의를 그대로 코드로 옮긴 것이다.
  • 신뢰도(conf)는 "아래꼬리가 몸통 대비 얼마나 긴가"와 "몸통이 얼마나 위쪽에 있는가"의 가중합이다 — 조건을 아슬아슬하게 넘긴 망치형보다 교과서적인 모양일수록 점수가 높다.

② VWAP 되돌림(레거시 셋업) 예시

③ v2 셋업 — 왜 다시 만들었나

레거시 셋업은 "모양"만 보고 신호를 냈고, "이게 진짜 살 만한 신호인지"는 전략의 종합점수 임계값에 전부 맡겼습니다. 실전 결과(43% 승률, 평균이익 1.92% vs 평균손실 −3.29%)를 분석해보니, 감지기 자체가 너무 헐렁하게 통과시키고 있었습니다. v2 셋업은 같은 아이디어(예: 눌림목)를 감지하되, 거래량 비율·몸통 크기(ATR 대비)· 종가 위치·추세 정렬을 감지기 안에서 직접 if 조건으로 강제합니다.

backend/src/pattern.rs
// v2_power_breakout: 20봉 신고가 + 거래량 2배 + 몸통 0.6 ATR + 상단 70% 마감

    && c.close > hh
    && vol_ratio >= 2.0
    && body_atr >= 0.6
    && cpos >= 0.7
    && c.close > e20

}
  • 다섯 조건이 전부 && 로 묶여 있다 — 하나라도 못 채우면 이 셋업은 아예 후보 목록에 오르지도 못한다. 레거시 셋업이 "일단 감지하고 나중에 점수로 거른다"였다면, v2는 "애초에 기준 미달이면 감지 자체를 안 한다".
  • ALL_PATTERNS/SETUP_PATTERNS/V2_SETUP_PATTERNS 세 개의 이름 목록 상수가 파일 위쪽에 있는데, 이게 프론트엔드 패턴 카탈로그(/api/patterns/catalog)와 전략 프리셋(strategy.rs)이 참조하는 "감지 가능한 신호의 전체 목록"이다.

연결: engine.rs 의 try_enter 와 backtest.rs 의 백테스트 루프가 이 세 감지기의 결과를 합쳐 하나의 후보 목록으로 만들고, strategy.rs 의 composite() 로 최종 점수를 매긴다.

backend/src/market.rs

market.rs — "지금 시장 전체가 오르는 중인가"

역할 한 줄: 코스피200 추종 ETF(기본값)를 하나의 대리 지표로 삼아, 시장이 위험선호(risk-on) 상태인지와 이 종목이 시장보다 잘 나가는지(상대강도)를 판단한다.

이 모듈이 생긴 배경이 중요합니다. 기존 로직은 "이 종목 자신의" 상위 타임프레임만 봤기 때문에, 지수가 오르는데도 정작 사고 있는 종목들은 다 하락하는 상황을 걸러내지 못했습니다. market.rs 는 실제 지수 코드 대신 "상장된 ETF 코드"(069500, KODEX 200)를 씁니다 — 그러면 별도의 지수 API 없이, 다른 종목과 똑같은 candle_fetcher.rs 경로로 조회할 수 있기 때문입니다.

backend/src/market.rs
pub fn assess_candles(proxy_code: &str, closed: &[Candle], rs_lookback: usize) -> MarketContext {
    if closed.len() < MIN_BARS {
        return MarketContext::unavailable(proxy_code);  // 데이터 부족 → "위험하지 않음"으로 간주(open)
    }
    let ema = ema_values(closed, REGIME_EMA);
    let above_ema = closed.last().unwrap().close > ema[ema.len() - 1];
    MarketContext {
        risk_on: above_ema && ema_slope_pct >= 0.0,
        above_ema,
        ret_pct: ret_over(closed, rs_lookback),
        // ...
    }
}
  • unavailable(proxy_code) 이 "위험하지 않음(risk_on: true)" 을 기본값으로 돌려주는 것에 주목한다 — 데이터를 못 가져왔다고 매매를 전부 멈추는(fail-closed) 대신, 판단을 보류하고 계속 진행하는(fail-open) 쪽을 택했다는 뜻이다. 다만 ret_pct 는 0으로 둬서, 상대강도 게이트가 있는 전략은 그 종목 자신의 절대수익률만으로 판단하게 만든다.
  • risk_on = above_ema && ema_slope_pct >= 0.0 — "종가가 EMA20 위에 있고, 그 EMA 자체도 하락 중이 아니다"라는 두 조건을 함께 요구한다. EMA가 이미 평활화된 값이라 한 봉의 노이즈로 쉽게 뒤집히지 않는다.

relative_strength() 는 "이 종목의 수익률 − 시장 대리 ETF의 수익률"을 퍼센트 포인트로 계산합니다. v2 전략들은 market_filter.min_rs 로 이 값에 최소 기준을 두어, "시장이 올라도 정작 못 따라가는 종목"을 걸러냅니다.

연결: strategy.rs 의 MarketFilter 가 이 판단을 켜고 끄며, engine.rs 의 try_enter 가 v2 전략의 진입 직전에 이 게이트를 통과시킨다.

backend/src/mtf.rs

mtf.rs — 상위 타임프레임이 같은 방향을 가리키는가

역할 한 줄: 1분봉에서 신호가 떴어도, 5분봉·15분봉 같은 상위 타임프레임이 하락 추세면 진입을 막거나 점수를 깎는다.

backend/src/mtf.rs
pub async fn higher_tf_uptrend(&self, token: &str, shcode: &str, base_tf: Timeframe, slope_tolerance: f64) -> bool {
    let uppers = base_tf.mtf_group();
    let Some(upper) = uppers.first() else { return true; };  // 상위TF가 없으면(일봉) 통과
    let candles = self.fetcher.fetch(token, shcode, *upper).await;
    if candles.len() < 6 { return true; }
    let closed = &candles[..candles.len() - 1];  // 아직 형성 중인 마지막 봉은 제외
    let tail = &closed[closed.len().saturating_sub(20)..];
    let mean = tail.iter().map(|c| c.close).sum::<f64>() / tail.len() as f64;
    trend_slope(tail) / mean >= -slope_tolerance.max(0.0)
}
  • let Some(upper) = uppers.first() else { return true; }; — "let...else" 패턴이다. uppers.first() 가 Some 이면 upper 에 값을 꺼내 계속 진행하고, None 이면 else 블록에서 함수를 즉시 끝낸다(여기선 true 반환). "값이 없으면 조기 종료"를 한 줄로 표현하는 관용구다.
  • &candles[..candles.len() - 1] — 형성 중인 마지막 봉을 제외하는 슬라이싱이다. 아직 마감되지 않은 봉의 종가는 언제든 바뀔 수 있으므로, 추세 판정은 항상 마감된 봉까지만 본다 — 이 원칙은 engine.rs·backtest.rs 전체에서 반복된다(미래 참조 방지).
  • trend_slope(tail) / mean >= -slope_tolerance.max(0.0) — 기울기를 가격 평균으로 나눠 "퍼센트 단위 기울기"로 정규화한 뒤, 허용 오차(slope_tolerance)보다 더 가파르게 내려갈 때만 진입을 막는다. 허용 오차가 0이면 "조금이라도 내려가면 차단"(엄격), 값을 키우면 완만한 하락 정도는 허용한다.

score() 메서드는 이와 별개로, 상위 타임프레임들 중 몇 개가 "지금도 매수 신호가 떠 있는 상태"인지 비율(0~1)로 계산합니다. 이 값은 진입을 막지는 않지만, strategy.rs 의 Source::Mtf 가중치를 통해 종합점수에 더해집니다.

연결: engine.rs 의 try_enter 가 진입 직전에 higher_tf_uptrend(게이트)와 score(가점) 둘 다 호출한다. backtest.rs 는 실거래와 같은 결과를 얻기 위해 MtfContext 라는 별도 구조체로 같은 계산을 미리 벡터화해둔다.

strategy.rs — 신호를 점수로, 전략을 세대로

역할 한 줄: 여섯 개 신호원(rule/atr/volume/mtf/ml/gaf)의 가중치, 어떤 패턴을 쓸지, 진입 기준을 하나의 StrategyConfig 로 묶는다.

backend/src/strategy.rs
pub enum Source { Rule, Atr, Volume, Mtf, Ml, Gaf }

pub struct StrategyConfig {
    pub weights: HashMap<Source, f64>,
    pub enabled_patterns: Vec<String>,
    pub entry_threshold: f64,
    pub risk_overrides: RiskOverrides,   // v2 전용, 레거시는 비어 있음
    pub market_filter: MarketFilter,     // v2 전용, 레거시는 꺼져 있음
    // ...
}

impl StrategyConfig {
    pub fn composite(&self, signals: &HashMap<Source, Option<f64>>) -> f64 {
        let active: Vec<(f64, f64)> = self.weights.iter()
            .filter_map(|(s, &w)| match signals.get(s) {
                Some(Some(v)) if w > 0.0 => Some((*v, w)),
                _ => None,
            })
            .collect();
        let total_w: f64 = active.iter().map(|(_, w)| w).sum::<f64>().max(1e-9);
        active.iter().map(|(v, w)| v * w).sum::<f64>() / total_w
    }
}
  • HashMap<Source, f64> — "신호원 → 가중치" 사전. 파이썬 dict[Source, float] 과 같다. Source 가 이 딕셔너리의 키로 쓰일 수 있는 이유는 선언부에 #[derive(Hash, Eq, PartialEq)] 가 붙어 있기 때문이다(=이 타입은 해시 가능하고 비교 가능하다고 컴파일러에게 알려준 것).
  • composite() 는 계산된 신호만 가중 평균에 넣는다 — filter_map 의 Some(Some(v)) if w > 0.0 부분이 "이 신호원의 값이 실제로 계산됐고(바깥 Some), 그 값이 있고(안쪽 Some), 가중치도 0보다 클 때만" 통과시킨다. 예를 들어 MTF 점수를 아직 계산하지 않은 시점(동기 스캔)이면 MTF 가중치가 있어도 분모에서 통째로 빠진다 — 그래야 "계산 안 한 신호의 가중치 때문에 점수가 부당하게 깎이는" 일이 없다.
  • filter_map — filter(거르기)와 map(변형)을 한 번에 하는 반복자 메서드다. 파이썬으로 치면 [f(x) for x in xs if f(x) is not None] 을 한 번의 순회로 하는 것과 같다.
레거시 vs v2 — 왜 세대를 나눴나

모의투자 130건을 분석한 결과, 승률 43%에 평균이익 +1.92% vs 평균손실 −3.29%로 기대값이 마이너스였습니다. 원인은 진입 패턴이 아니라 손절이 설정값보다 훨씬 크게 미끄러진 것(고정 1.5% 손절이 봉 마감 기준으로만 평가되어 실제로는 평균 −3.42%에 체결)과 시장 상황을 전혀 안 본다는 것이었습니다. 그래서 v2 프리셋은 진입 신호뿐 아니라 RiskOverrides(ATR 비례 손절 강제 + 봉 중간 실시간 손절)와 MarketFilter(시장 위험선호 확인)를 전략 자체에 내장해서, 사용자가 폼에서 뭘 잘못 입력해도 이 보호 장치가 벗겨지지 않게 만들었습니다. resolve() 함수의 테스트 (resolve_cannot_strip_v2_protections_via_weight_tweaks)가 바로 이걸 보장합니다.

연결: enabled_patterns 목록은 pattern.rs 의 상수 이름들과 문자열로 매칭된다. risk_overrides 는 risk.rs 의 RiskConfig 위에 얹혀 "실제로 거래할 리스크 설정"(effective_risk)을 만든다.

역할 한 줄: 모든 진입은 can_enter_with() 를 통과하고 position_size_with() 로 수량이 정해져야 한다. 청산 판단도 전부 이 파일이 한다.

backend/src/risk.rs
pub struct RiskManager {
    pub cfg: RiskConfig,
    daily_pnl: f64,
    positions: HashMap<String, Position>,   // 종목코드 → 보유 포지션
}

impl RiskManager {
    pub fn position_size_with(&self, equity: f64, entry: f64, atr: f64, cfg: &RiskConfig) -> i64 {
        let (stop_distance, _) = cfg.stop_target_dists(entry, atr);
        let qty_by_risk = (equity * cfg.risk_per_trade_pct / stop_distance) as i64;
        let qty_by_cap = (equity * cfg.max_position_pct / entry) as i64;
        qty_by_risk.min(qty_by_cap).max(0)
    }

    pub fn check_exit_with(&mut self, code: &str, price: f64, atr: f64, cfg: &RiskConfig) -> Option<&'static str> {
        let pos = self.positions.get_mut(code)?;
        pos.peak = pos.peak.max(price);
        let trail = pos.peak - atr * cfg.trailing_stop_atr;
        if price <= pos.stop { Some("stop_loss") }
        else if price >= pos.target { Some("take_profit") }
        else if price <= trail && price > pos.entry { Some("trailing_stop") }
        else { None }
    }
}
  • position_size_with — 수량은 두 가지 상한 중 더 작은 쪽이다. "손절까지의 거리로 계산한 리스크 기준 수량"(계좌의 1%만 잃도록)과 "종목당 최대 비중 기준 수량"(계좌의 10%를 넘지 않도록) 중 작은 값을 쓴다 — 어느 한 쪽만으로는 손절폭이 좁은 종목에 몰빵하거나, 반대로 손절폭이 넓은 종목에 계좌를 다 거는 상황을 막지 못하기 때문이다.
  • let pos = self.positions.get_mut(code)?; — get_mut 은 값을 바꿀 수 있게 빌려온다(2-8 참고). 그 뒤의 ? 는 "이 종목이 아예 보유 중이 아니면(None) 이 함수도 즉시 None 을 반환하고 끝내라"는 뜻이다.
  • 손절/익절/트레일링 세 가지 중 무엇에 걸렸는지를 Option<&'static str>(정적 문자열 하나 또는 없음)로 돌려준다. 호출자(engine.rs)는 이 사유 문자열을 그대로 거래 일지와 텔레그램 알림에 사용한다.
  • trail = pos.peak - atr * cfg.trailing_stop_atr — 트레일링 스탑은 "진입 이후 가장 높았던 가격(peak)에서 ATR의 배수만큼 내려온 선"이다. 가격이 오를수록 이 선도 따라 올라가지만, 절대 내려가지는 않는다(pos.peak = pos.peak.max(price)).

이 외에 can_average/average_down 이 피보나치 물타기 (fib(n) = 1,1,2,3,5,...배로 수량을 늘려가며 평단을 낮추는 것)를, daily_loss_ok 가 "오늘 실현+미실현 손실이 한도를 넘었는가"를 판단합니다. restore_positions/sync_position 은 서버 재시작이나 실전 계좌와의 대사(reconcile)를 위한 것으로, engine.rs 가 씁니다.

연결: engine.rs 의 try_enter/manage_open 이 이 파일의 게이트·사이징·청산판단을 그대로 실행에 옮기고, backtest.rs 는 같은 함수를 과거 데이터에 대해 반복 호출해 검증한다.

pub fn wilson_lower_bound(wins: u64, n: u64) -> f64 {
    let z = 1.645_f64; // 95% 단측 신뢰
    let p = wins as f64 / n as f64;
    let z2 = z * z;
    let centre = p + z2 / (2.0 * n as f64);
    let margin = z * ((p * (1.0 - p) + z2 / (4.0 * n as f64)) / n as f64).sqrt();
    ((centre - margin) / (1.0 + z2 / n as f64)).clamp(0.0, 1.0)
}
  • "3전 3승(100%)" 이 "100전 70승(70%)" 보다 못하다는 걸 숫자로 표현한 함수다. 표본이 적을수록 승률의 하한을 더 크게 깎아서, 소표본 과대평가를 막는다. 관심종목을 승률로 줄 세울 때 이 하한값을 기준으로 쓴다.
  • u64 — 부호 없는 64비트 정수(음수가 될 수 없는 정수). 승리 횟수나 표본 수처럼 "절대 음수일 수 없는" 값에 이 타입을 쓰면, 실수로 음수가 들어갈 수 있는 코드 경로 자체가 컴파일되지 않는다.

마지막으로 evaluate_strategy_live() 가 워크포워드(walk-forward) OOS(out-of-sample) 검증을 수행합니다 — 데이터를 4개 구간으로 나눠 각 구간을 "이전 구간들로 학습한 전략을 처음 보는 구간에 시험한다"는 식으로 검증하고, 평균 수익이 양수이고 4구간 중 60% 이상에서 이겼고 신호가 10건 이상일 때만 tradeable: true 를 매깁니다. 각 구간 앞에는 EMA50 워밍업에 필요한 55봉을 추가로 붙여주는데(WARMUP_BARS), 이게 없으면 v2 셋업은 짧은 구간 안에서 지표 예열도 못 끝내고 "신호 없음"으로 오판됩니다.

async fn run_loop(deps: Arc<Deps>, state: Arc<Mutex<State>>, poll_sec: u64, resume: bool) {
    loop {
        if !state.lock().await.running { break; }
        if market_open(&*state.lock().await) {
            let token = resolve_token(&deps).await;
            let _ = scan_and_trade(&deps, &state, &token).await;
            state.lock().await.persist(deps.broker.mode);   // 재시작 대비 스냅샷 저장
        }
        let mut slept = 0u64;
        while slept < poll_sec.max(1) {
            tokio::time::sleep(std::time::Duration::from_secs(1)).await;
            slept += 1;
            if !state.lock().await.running { return; }   // 1초마다 정지 신호 확인
        }
    }
}
  • poll_sec 초를 한 번에 sleep 하지 않고 1초씩 쪼개어 잔다 — 사용자가 "정지" 버튼을 눌렀을 때 최대 1초 안에 반응하기 위해서다. 60초 주기로 설정했다고 정지 요청이 60초씩 묵히면 안 되기 때문이다.
  • market_open(&*state.lock().await) — 평일 09:00~15:20(KST)이 아니거나 휴장일이면 scan_and_trade 자체를 건너뛴다. ignore_market_hours 설정을 켜면 이 체크를 건너뛸 수 있지만(백테스트/야간 테스트용), 장 마감 강제청산(EOD flatten) 게이트는 이 설정과 무관하게 항상 살아있다 — 야간 무시 설정이 "마감 리스크 관리까지 끄는" 사고를 막기 위해서다.

역할 한 줄: 신호 판단부터 리스크 게이트까지는 모의/실전이 완전히 같은 코드를 쓰고, 매수/매도 딱 그 순간만 여기서 갈린다.

    // ... 지정가는 t0425를 폴링해 실제 체결수량을 확인 후 반환 ...
}
  • 모의투자는 신청가에 즉시 전량 체결된 것으로 가정한다 — 실제 슬리피지는 없지만, 신호·게이트·사이징 로직을 실전과 동일하게 검증하는 목적에는 이걸로 충분하다.
  • 실전 지정가 주문은 접수와 체결이 다르다 — 주문을 넣었다고 바로 다 체결되는 게 아니므로, order_fill_status(t0425)를 최대 5번 3초 간격으로 폴링해 실제 체결수량/평균가를 확인하고, 시간 내 다 안 되면 잔량을 취소한 뒤 체결된 만큼만 Fill 로 돌려준다.
  • Fill 구조체(ok, fill_price, qty)가 이 파일의 유일한 반환 계약이다 — 호출자(engine.rs)는 이 세 값만 보고 나머지(포지션 등록, 현금 차감, 일지 기록)를 처리하므로, 모의든 실전이든 그 이후 로직은 완전히 같다.

연결: engine.rs 의 try_enter/exit/fib_average_down 이 유일한 호출자다. ebest.rs 의 place_order/order_fill_status/cancel_order 를 감싼다.

journal.rs — 청산될 때마다 한 줄씩 남는 기록

역할 한 줄: 모든 청산을 JSON Lines 파일 한 줄로 영구 기록하고, 승률/손익비 같은 통계를 계산해준다.

backend/src/journal.rs
pub struct TradeJournal {
    path: PathBuf,
    lock: Mutex<()>,
}

pub fn record(&self, trade: &TradeRecord) {
    let _g = self.lock.lock().unwrap();
    if let Ok(line) = serde_json::to_string(trade) {
        let mut f = std::fs::OpenOptions::new().create(true).append(true).open(&self.path).unwrap();
        writeln!(f, "{line}").unwrap();
    }
}
  • Mutex<()> — 잠글 데이터가 없는 뮤텍스다. 여기서 지키려는 건 특정 값이 아니라 "이 파일에 동시에 두 스레드가 쓰지 못하게 하는 것" 그 자체이므로, 속을 빈 튜플(())로 둔 것이다.
  • JSON을 배열로 저장하지 않고 한 줄에 하나씩(JSONL) 저장한다 — 거래가 새로 생길 때마다 파일 전체를 다시 읽고 파싱하고 다시 쓰는 대신, 파일 끝에 한 줄만 추가(append)하면 되므로 거래가 몇만 건이 쌓여도 기록 비용이 항상 일정하다.
  • stats() 는 승수/패수, 손익비(profit_factor = 총이익 ÷ 총손실), 평균수익률 등을 계산해 API로 그대로 내보낸다 — validation.rs 의 실전 투입 체크리스트가 이 숫자들을 기준으로 판단한다.

연결: engine.rs 의 record_close 가 청산마다 이 파일에 기록을 남기고, routers/trading.rs 의 /api/trading/journal·/stats 가 이 기록을 읽어 화면에 보여준다.

validation.rs — "실전 투입해도 될까?" 체크리스트

역할 한 줄: 모의투자 기록이 최소 거래수/기간/승률/손익비 기준을 넘었는지 평가한다 — 단, 권고일 뿐 실전을 막지는 않는다.

backend/src/validation.rs
pub fn evaluate(journal: &TradeJournal, c: &ReadinessCriteria) -> Value {
    let trades = journal.by_mode("paper");
    let s = paper_stats(&trades);
    let checks = vec![
        criterion("trades", "페이퍼 거래 수", g("trades") >= c.min_paper_trades as f64, ...),
        criterion("win_rate", "승률", g("win_rate") >= c.min_win_rate, ...),
        // ...
    ];
    let ready = checks.iter().all(|c| c["passed"].as_bool().unwrap_or(false));
    json!({"ready": ready, "criteria": checks, "stats": s})
}
  • checks.iter().all(|c| ...) — "모든 원소가 조건을 만족하는가"를 검사하는 반복자 메서드. 파이썬의 all(cond(c) for c in checks) 와 정확히 같다. 다섯 개 기준(거래수·기간·승률·손익비·누적손익) 중 하나라도 미달이면 ready 는 false.
  • 이 결과는 routers/trading.rs 의 /api/trading/start 에서 "advisory"(권고)로만 응답에 실린다 — 기준 미달이어도 사용자가 실전을 선택하면 막지 않는다. 다만 그 사실은 화면에 경고로 분명히 뜬다.

연결: journal.rs 의 모의투자 기록을 읽고, routers/trading.rs 의 readiness()/start_engine() 이 이 결과를 화면과 시작 응답에 함께 보낸다.

pub async fn send_to(&self, chat_id: &str, text: &str) -> Result<(), String> {
    let url = format!("{}{}/sendMessage", self.base_url, self.token);
    for chunk in split_chunks(text, 3900) {   // 텔레그램 4096자 제한 대응
        let resp = self.client.post(&url).json(&json!({"chat_id": chat_id, "text": chunk})).send().await
            .map_err(|e| format!("텔레그램 요청 실패: {e}"))?;
        if !resp.status().is_success() {
            return Err(format!("텔레그램 전송 실패: {}", resp.text().await.unwrap_or_default()));
        }
    }
    Ok(())
}
  • .map_err(|e| format!("텔레그램 요청 실패: {e}"))? — Result 의 에러 타입을 바꿔치기하는 관용구다. reqwest::Error 그대로는 이 함수의 반환 타입(Result<(), String>)과 안 맞으므로, 실패했을 때만 사람이 읽을 문자열로 바꾼 뒤 ? 로 그대로 전파한다.
  • 명령 리스닝은 get_updates(롱폴링)로 구현된다 — 텔레그램 서버에 "새 메시지 있으면 최대 30초까지 기다렸다가 알려줘"라고 요청하고, 응답이 오면 곧바로 다시 요청하는 식으로 반복한다. main.rs 의 spawn_telegram_commands 가 이 함수를 무한 루프로 돌린다.
  • parse_command 는 Command 라는 enum 으로 명령을 분류한다 — /chk, /chk1~3, /start, /stop, /help 외의 텍스트는 전부 None(무시)이 된다.

연결: engine.rs 의 notify() 가 거래 이벤트를, main.rs 의 spawn_position_watcher/spawn_telegram_commands 가 상태 보고/명령 응답을 이 파일을 통해 내보낸다. 시나리오 E에서 /chk 명령 하나가 처리되는 전체 경로를 봅니다.

routers/ — HTTP 엔드포인트

역할 한 줄: /api/... 요청을 받아, 위에서 본 모듈들을 호출하고 JSON으로 응답한다. 로직 자체는 거의 없다 — 얇은 접착제 역할.

6개 파일이 있고, 전부 같은 뼈대를 반복합니다: 매개변수 구조체 정의(기본값 포함) → async fn 핸들러 → Router::new().route(...).

backend/src/routers/candles.rs
#[derive(Deserialize)]
struct TfQuery {
    #[serde(default = "default_tf")]
    tf: String,
}
fn default_tf() -> String { "5m".into() }

async fn get_candles(
    State(st): State<AppState>,
    Path(shcode): Path<String>,
    Query(q): Query<TfQuery>,
) -> ApiResult {
    let tf = parse_tf(&q.tf)?;
    let token = st.token().await?;
    let candles = st.fetcher.fetch(&token, &shcode, tf).await;
    Ok(Json(json!({ "candles": candles })))
}

pub fn router() -> Router<AppState> {
    Router::new().route("/api/candles/:shcode", get(get_candles))
}
  • State(st): State<AppState>, Path(shcode): Path<String>, Query(q): Query<TfQuery> — axum의 추출자(extractor)다. 함수 매개변수의 타입만 보고 axum이 "URL 경로에서 shcode 를 뽑고, 쿼리스트링을 TfQuery 로 파싱하고, 공유 상태를 꺼내 넘겨줘"를 자동으로 해준다. 파이썬 FastAPI의 Depends()/경로 매개변수와 정확히 같은 발상이다.
  • #[serde(default = "default_tf")] — 요청에 tf 쿼리 파라미터가 없으면 default_tf() 함수의 반환값("5m")을 대신 쓴다. FastAPI의 tf: str = "5m" 기본 인자와 같은 자리다.
  • parse_tf(&q.tf)?, st.token().await? — 앞서 2-7에서 본 ? 연산자가 여기서 실제로 쓰인다. 타임프레임 문자열이 잘못됐거나 eBest 인증이 실패하면, 핸들러는 그 자리에서 즉시 에러 응답(400/503)으로 끝난다 — 이후 줄은 아예 실행되지 않는다.

6. 기능별로 코드 따라가기

이제까지는 파일 하나하나를 봤습니다. 이번엔 반대로, 실제로 프론트엔드에서 버튼을 눌렀을 때 요청 하나가 어떤 파일들을 순서대로 거쳐 가는지 다섯 가지 시나리오로 따라갑니다. 각 단계는 위에서 이미 설명한 코드를 다시 가리키므로, 모르는 용어가 나오면 링크를 눌러 위로 돌아가면 됩니다.

시나리오 A — 차트 캔들 조회

GET /api/candles/005930?tf=5m

  1. routers/candles.rs 의 get_candles 가 요청을 받아 tf 문자열을 Timeframe::parse 로 변환한다. 잘못된 값(예: "7m")이면 여기서 즉시 400 에러로 끝난다.
  2. st.token().await? — state.rs 를 통해 ebest.rs 의 auth_token 을 호출한다. 캐시된 토큰이 아직 유효하면 네트워크 호출 없이 즉시 반환된다.
  3. st.fetcher.fetch(&token, "005930", Timeframe::M5) — candle_fetcher.rs 가 먼저 90초 TTL 캐시를 확인한다. 캐시가 없거나 만료됐으면 ebest.rs 의 fetch_minute_candles(TR t8452)를 호출하고, 응답 JSON을 normalize_minute() 으로 Vec<Candle> 로 바꿔 캐시에 채운 뒤 돌려준다.
  4. 핸들러가 이 캔들 배열을 그대로 json!({...}) 에 담아 응답한다. 프론트엔드는 이 JSON을 그대로 차트 라이브러리에 넘긴다(프론트엔드 코드는 이 문서의 범위 밖).

시나리오 B — 패턴 신호 스캔

GET /api/patterns/005930?tf=5m&strategy=balanced&mtf=true

  1. routers/patterns.rs 의 get_patterns 가 strategy::preset("balanced") 로 strategy.rs 의 StrategyConfig 를 불러온다.
  2. 시나리오 A와 같은 경로로 캔들을 가져온 뒤, st.detector.scan(&candles, tf, 0.0, true, &cfg, 1) 을 호출한다 — pattern.rs 의 PatternDetector::scan 이 창을 뒤로 밀며 8개 캔들스틱 패턴 감지기를 전부 돌리고, ATR/거래량 확인까지 마친 PatternResult 목록을 만든다.
  3. mtf=true 이면 mtf.rs 의 MtfEngine::score 로 상위 타임프레임 컨플루언스를 계산해 각 결과의 mtf_score 를 채우고, apply_strategy() 로 종합점수를 다시 계산한다.
  4. 마지막 봉 하나에 대해 session.rs·pattern.rs 의 detect_setups()(VWAP/ORB/EMA 셋업)도 함께 돌려 후보 목록에 합친다.
  5. 전체 결과를 composite_score 내림차순으로 정렬해 응답한다 — 화면에는 가장 유력한 신호가 맨 위에 뜬다.

시나리오 C — 백테스트 (전략 × 종목 매트릭스)

POST /api/backtest/strategy-matrix — { "shcodes": [...], "tf": "auto" }

  1. routers/backtest.rs 가 워치리스트의 각 종목에 대해, tf: "auto" 라면 각 전략이 원래 튜닝된 타임프레임(예: 단타 프리셋은 1분봉, 반전패턴 프리셋은 5분봉)으로 각각 조회한다.
  2. candle_fetcher.rs 의 fetch_history() 로 500~2000봉의 깊은 과거 데이터를 연속조회(cts)로 이어붙여 가져온다(실시간 캐시와는 별도 캐시).
  3. 같은 (종목, 타임프레임) 캔들에 대해 backtest.rs 의 MtfContext::build() 를 딱 한 번 만들어, 이후 모든 전략이 이걸 재사용한다(상위 타임프레임을 전략마다 따로 조회하지 않기 위해).
  4. 전략 프리셋마다 run_strategy_backtest()(인샘플)와 evaluate_strategy_live()(워크포워드 OOS)를 돌린다. v2 전략은 이 단계에서 자신의 effective_risk()(ATR 강제 손절 등)를 적용해 자기 자신의 리스크 규칙으로 검증받는다.
  5. 모든 (종목, 전략) 조합의 결과가 매트릭스로 응답된다. 프론트엔드 대시보드는 이 중 각 종목의 oos_avg_return 이 가장 높으면서 tradeable: true 인 전략을 골라 관심종목·전략 배정을 자동으로 채운다.

시나리오 D — 자동매매 시작부터 한 번의 매수까지

POST /api/trading/start 로 시작해, 백그라운드 루프가 실제로 매수 주문을 낼 때까지

  1. 시작 요청 처리 — routers/trading.rs 의 start_engine() 이 전략(strategy::resolve), 종목별 전략 배정, 워치리스트, 리스크 설정을 body에서 파싱한다. require_tradeable: true 면 backtest.rs 의 evaluate_strategy_live 로 OOS 검증을 통과 못 한 종목을 미리 걸러낸다.
  2. 엔진 생성 또는 재사용 — 이미 같은 모드로 도는 엔진이 있으면 설정만 바꾸고(reconfigure) 포지션·현금은 그대로 둔다. 새로 만드는 경우 TradingEngine::new() 후 restore_snapshot() 으로 직전 engine_state_{mode}.json 을 복원한다 — 서버가 재시작됐어도 보유 포지션의 손절/익절 관리가 끊기지 않는 이유가 여기 있다.
  3. 루프 진입 — engine.start(poll_sec, resumed) 이 engine.rs 의 run_loop 를 백그라운드로 띄운다. 동시에 save_autostart() 가 이 시작 설정을 디스크에 저장해, 서버가 죽었다 다시 뜨면 main.rs 부팅 3초 뒤 자동으로 재개되게 한다.
  4. 사이클마다 재매수 가드 확인 — 종목이 관심종목이고 아직 미보유일 때, try_enter() 는 제일 먼저 "직전에 이 종목에서 손절당한 적이 있고, 아직 그 가격을 회복 못 했거나 쿨다운 봉수가 안 지났는지"부터 본다. 걸리면 그 자리에서 재매수가드 상태로 끝난다 — 손절 직후 같은 가격에 바로 다시 사는 "휩소(whipsaw)"를 막기 위해서다.
  5. 신호 후보 모으기 — pattern.rs 의 scan()(캔들스틱 패턴) + detect_setups()(레거시 셋업) + detect_v2_setups()(v2 셋업)을 합쳐 하나의 후보 목록을 만들고, 이 전략이 enabled_patterns 에 켜둔 패턴만 남긴다.
  6. 확인봉 대기 — require_confirmation 이 켜져 있으면, 패턴이 뜬 바로 다음 봉이 아니라 "패턴 발생 후 confirm_window_bars 봉 안에 그 패턴의 고점을 넘는 확인봉이 나왔는가"까지 봐야 진입 후보가 된다. 확인이 아직 안 됐지만 대기 창 안에 있으면 확인봉대기 상태로 다음 사이클을 기다린다.
  7. v2 시장 필터 — 전략에 market_filter 가 켜져 있으면, market.rs 로 시장 대리 ETF가 위험선호 상태인지, 이 종목이 시장보다 잘 나가는지(상대강도)를 확인한다. 둘 중 하나라도 기준 미달이면 시장위험/상대약세 상태로 진입을 건너뛴다.
  8. 상위TF 추세 + MTF 점수 — mtf.rs 로 상위 타임프레임이 뚜렷한 하락세면 상위TF역행으로 차단하고, 아니면 MTF 컨플루언스 점수를 종합점수에 반영해 다시 계산한다.
  9. 비용/리스크 게이트 — passes_entry_gates() 가 종합점수 임계값, 거래량 확인 필요 여부, 손절 대비 목표가 비율(reward:risk), 왕복 매매비용 대비 기대 수익(edge-over-cost)을 전부 통과해야 한다. 이어서 risk.rs 의 can_enter_with() 가 일일 손실 한도와 최대 보유종목수를 확인한다.
  10. 수량 계산 & 매수 — risk.position_size_with() 로 수량을 정하고, max_buy_amount(포트폴리오 전체 진입금액 한도)와 보유 현금으로 다시 한 번 상한을 씌운 뒤 broker.rs 의 buy() 를 호출한다. 체결되면 risk.register() 로 포지션을 등록하고, 스냅샷을 저장하고(persist), 거래 이벤트를 남기고, telegram.rs 로 알린다.
  11. 다음 사이클부터는 관리 모드 — 이제 이 종목은 manage_open() 경로를 탄다. hard_stop_intrabar 가 켜져 있으면 형성 중인 봉의 실시간가로도 손절을 확인하고(캔들 캐시가 아니라 t1101 현재가를 직접 조회), 아니면 봉이 마감될 때만 risk.rs 의 check_exit_with()(손절/익절/트레일링)로 청산 여부를 판단한다. 손절 조건에 걸렸는데 피보나치 물타기가 켜져 있고 일일 손실 한도에 여유가 있으면, 매도 대신 fib_average_down() 으로 추가 매수해 평단을 낮춘다.
이 설계에서 배울 점

10단계 전부가 닫힌 봉(closed bar) 을 기준으로 판단합니다 — 형성 중인 마지막 봉의 가격은 하드스탑 확인에만 쓰이고, 신호 감지·진입·일반 청산은 전부 마감된 봉으로만 결정됩니다. 이 원칙 하나가 mtf.rs, backtest.rs, engine.rs 세 파일 모두에서 반복되는데, 지금 보이는 가격으로 방금 지나간 신호를 미래참조해서 사고파는 것을 막기 위해서입니다.

시나리오 E — 텔레그램 /chk 명령

사용자가 stock_monitor 방에 /chk1 을 입력했을 때

  1. main.rs 의 spawn_telegram_commands 백그라운드 작업이 telegram.rs 의 get_updates() 롱폴링으로 이 메시지를 받는다.
  2. parse_command("/chk1") 이 Command::Chk(ChkKind::Status) 로 분류한다. 인가된 방(설정된 chat_id)이 아니면 이 시점에서 조용히 무시된다.
  3. main.rs 의 handle_telegram_command 가 st.engine.lock().await.clone() 로 현재 엔진을 꺼내고, telegram.rs 의 build_chk() 를 호출한다.
  4. build_chk 는 engine.status()(engine.rs의 전체 상태 스냅샷)를 가져와 status_section() 으로 "실행상태·모드·현금·평가자산·일손익" 텍스트를 만든다.
  5. 완성된 텍스트를 send_to(chat_id, text) 로 되돌려 보낸다 — 4096자를 넘으면 split_chunks() 가 줄 경계에서 여러 메시지로 나눈다.
